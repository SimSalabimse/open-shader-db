# Upload-manifest golden vectors

Shared fixtures for `crates/upload` and `worker/`. Each `*.json` file
is one case.

| Field | Meaning |
| --- | --- |
| `verdict` | `accept` or `reject` |
| `error_code` | Worker / `Error::code()` string, or `null` on accept |
| `body` | JSON value; encoded compact with sorted keys for the parser |
| `body_text` | Exact UTF-8 payload (duplicate keys, trailing tokens) |
| `body_hex` | Exact bytes, lowercase hex (BOM, non-UTF-8) |

A file uses exactly one of `body`, `body_text`, or `body_hex`.

`index.json` lists every vector path, verdict, and error code. Accept
entries also list a `stored/` file: the compact JSON the Worker must
persist, generated by the Rust canonicalizer. Both language runners
require the on-disk vector set and the stored-bytes set to match
`index.json` exactly, so deleting a vector or its expected-bytes file
fails. An unknown `verdict` is a hard error.

Valid `body` values are produced by `osdb-upload` (canonical
`UploadManifest`). `body_text` / `body_hex` cover pretty-printed,
escaped, unsorted-key, and other non-compact inputs; stored bytes
still pin the canonical form. Invalid cases are hand-written. Both
language test suites walk this directory and run every file. The JSON
Schema is **not** the oracle; several reject cases are schema-valid.

Schema version 1 fixtures omit `pipeline_hashes`. Schema version 2
fixtures include that array (sorted unique lowercase hex, cap
50 000). A version 1 document that carries the field is
`UNKNOWN_FIELD`. Any other `schema_version` is
`UNSUPPORTED_SCHEMA_VERSION`. Version 2 without the field is
`MISSING_FIELD`.
